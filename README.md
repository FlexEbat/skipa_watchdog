# Skipa Watchdog

Skipa Watchdog следит за сетевыми подключениями к серверу, сверяет источник
с базой IP-адресов сканеров CyberOK/Skipa, ГРЧЦ и НКЦКИ (+ дополнительные
списки), и при обнаружении **блокирует** такой IP и/или присылает
**уведомление** — режим настраивается. Блокировка работает не только для
самого хоста, но и для сервисов, опубликованных через **Docker и
Kubernetes**.

Два полностью независимых по реализации и зависимостям варианта установки:

- **Только сервис** — весь мониторинг и блокировка сделаны на **чистом
  bash** (+ `iptables`/`ipset`, оба обычно уже стоят на любом сервере).
  **Python не используется вообще** — ни на этапе установки, ни во время
  работы.
- **Сервис + Telegram-бот** — то же самое плюс уведомления и команды/меню в
  чате. Это единственный сценарий во всём проекте, где нужен Python
  (`watchdog.py`, свой `venv`, `python-telegram-bot`).

`install.sh` спрашивает, какой вариант ставить, прямо при первом запуске —
подробнее ниже.

## Как это работает

### Только сервис (bash)

Весь список IP-адресов загружается в **ipset** — именованный набор IP/CIDR,
который ядро Linux хранит и матчит само, без единого демона в userspace.
Два независимых ipset:

- `skipa-scanners` — автообновляемый базовый список (CyberOK/Skipa, ГРЧЦ,
  НКЦКИ + доп. список), целиком пересобирается при каждом обновлении
  (`service/sync-lists.sh`, атомарная подмена через `ipset swap` — без окна,
  когда список пуст или наполовину загружен).
- `skipa-manual` — ручные блокировки администратора (`blockctl.sh` / пункт
  меню 6), не зависит от автообновления - список обновляется, а ручные
  блокировки остаются на месте.

`iptables`-правила (`-m set --match-set ...`) на `INPUT`
(+ `DOCKER-USER`/`KUBE-*`, если есть) матчят трафик против обоих ipset и, в
зависимости от `ACTION_MODE`, логируют и/или дропают его — целиком в ядре.
При режиме `block` (без уведомлений) в userspace вообще не остаётся ни
одного постоянно работающего процесса — только периодический таймер
обновления списка раз в несколько дней.

### Сервис + Telegram-бот (Python)

Единая точка входа `watchdog.py`: мониторит соединения (через
`/proc/net/tcp` и/или чтение kernel-лога), при совпадении с базой блокирует
через свою собственную динамическую цепочку iptables (`SKIPA-BLOCK`) и
присылает уведомление в Telegram + пишет в локальный лог. Подробности - в
разделах ниже.

## Что делает при обнаружении

Поведение задаётся режимом действия (в bash-варианте — `ACTION_MODE` в
`service.conf`, в python-варианте — `action.mode` в `config.yaml`; меняется
из одного и того же пункта меню `install.sh` независимо от варианта
установки):

| Режим | Что происходит |
|---|---|
| `block_notify` (по умолчанию) | IP блокируется **и** отправляется уведомление |
| `block` | Только блокировка, без уведомлений (в bash-варианте - вообще без работающего процесса) |
| `notify` | Только уведомление, IP не блокируется |

## Установка

Первый запуск показывает только описание и предложение установить (без
меню — устанавливать пока нечего):

```bash
curl -fsSL https://raw.githubusercontent.com/FlexEbat/skipa_watchdog/main/install.sh -o install.sh
sudo bash install.sh
```

(либо `git clone https://github.com/FlexEbat/skipa_watchdog.git && cd skipa_watchdog && sudo bash install.sh`,
если предпочитаете иметь репозиторий локально — разницы никакой, `install.sh`
сам клонирует актуальный код в `/opt/skipa_watchdog`)

Дальше — выбор варианта:

```
Как установить?
  1) Только сервис - мониторинг + блокировка на bash + iptables/ipset.
     Python не используется вообще: ни для установки, ни для работы.
  2) Сервис + Telegram-бот - то же самое, и дополнительно уведомления и
     команды/меню в чате (единственное место в проекте, где нужен
     Python: venv + python-telegram-bot).
```

Из системных требований нужен только `git` (и то не обязательно — `install.sh`
сам определит пакетный менеджер и поставит его при необходимости). Для
варианта 1 больше вообще ничего не требуется: `install.sh` доустановит
`ipset`/`curl`, если их почему-то нет. Для варианта 2 таким же образом
доустанавливается `python3`.

В конце регистрируется команда `skipa-watchdog` — **дальше для управления
используйте именно её**, а не полный путь до `install.sh`:

```bash
sudo skipa-watchdog
```

Повторный запуск (когда всё уже установлено) сразу показывает меню:

```
======================================
 Skipa Watchdog
 Версия: 3.0.0
======================================
 1) Проверка работоспособности
 2) Управление сервисом (start/stop/restart/статус)
 3) Настройки обнаружения (список IP / режим действия)
 4) Telegram (подключить/отключить)
 5) Docker/Kubernetes (логирование + блокировка)
 6) Заблокированные IP
 7) Принудительно обновить базу IP
 8) Просмотр логов
 9) Редактировать конфиг вручную
10) Обновить Skipa Watchdog
11) Удалить полностью
 0) Выход
```

Все пункты меню работают одинаково независимо от того, какой вариант
установлен — `install.sh` сам знает, что стоит (`bash` или `python`), и
использует нужный набор команд под капотом.

Docker/Kubernetes проверяются и настраиваются один раз, сразу после первой
установки — повторно это не спрашивается само, но доступно из меню в любой
момент (пункт 5). При каждом запуске `install.sh`/`skipa-watchdog`
дополнительно проверяет, не вышли ли новые версии подключённых списков IP.

### Переключение между вариантами

Начать можно с "только сервис", а Telegram подключить позже, в любой момент,
из меню (пункт 4 → "Подключить/перенастроить"). В этот момент `install.sh`
сам создаст `venv`, поставит `python-telegram-bot`, перенесёт текущие
настройки (список/режим действия) из `service.conf` в новый `config.yaml`, и
переключит systemd-юнит на python-процесс. Автообновление базового ipset-списка
(`skipa-scanners`) при этом **не останавливается** — блокировка на уровне
ядра продолжает работать независимо от Python, а бот добавляется поверх как
дополнительный источник уведомлений. Обратного переключения (с бота обратно
на чистый bash) из меню нет — для этого проще удалить (пункт 11) и
установить заново с вариантом 1.

Неинтерактивный режим для автоматизации:

```bash
sudo bash install.sh install        # установить/обновить (git pull + зависимости)
sudo bash install.sh uninstall      # удалить полностью
sudo bash install.sh status         # краткий статус без меню
sudo bash install.sh fw-rules       # поставить правила логирования/блокировки docker/k8s
sudo bash install.sh check-lists    # проверить обновления списков прямо сейчас
```

### Установка вручную (без install.sh)

Только сервис (bash, без Python):

```bash
sudo apt install ipset curl        # или аналоги для вашего пакетного менеджера
cp service/service.conf.example service.conf
nano service.conf
sudo bash service/sync-lists.sh service.conf        # заполнить ipset
sudo bash service/setup-ipset-rules.sh block_notify  # поставить iptables-правила
sudo bash service/notify-tail.sh service.conf        # (опционально) демон detections.log
```

С Telegram (нужен venv под `python-telegram-bot`):

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
pip install -r requirements-telegram.txt

cp config.example.yaml config.yaml
nano config.yaml   # заполнить telegram.bot_token/chat_id
sudo bash install-firewall-rules.sh
python watchdog.py
```

## Зависимости

**Только сервис:** ноль пакетов сверх того, что почти наверняка уже стоит
на сервере (`bash`, `iptables`, `ipset`, `curl`). Ни `pip`, ни `python3`, ни
`venv` не устанавливаются и не запускаются — процесса, который можно было
бы назвать "интерпретатором", в этом варианте попросту нет, только
`iptables`/`ipset` (ядро) и несколько bash-скриптов, вызываемых по таймеру.

**Сервис + Telegram-бот:** `python-telegram-bot` и его зависимости
(`httpx`, `anyio`, `APScheduler` и т.д.) ставятся в отдельный `venv` только
для этого варианта — ~29 МБ на диске, ~12–15 МБ памяти сверх базового
процесса. Сам `watchdog.py` использует только stdlib (HTTP — через `urllib`
в потоке, без `aiohttp`; мониторинг — через чтение `/proc/net/tcp`, без
`psutil`) плюс единственный пакет `PyYAML` для чтения `config.yaml`.

| | Доп. место на диске | Память процесса (RSS) |
|---|---|---|
| Только сервис | **0** (только код проекта, ~30 КБ bash-скриптов) | **0** в режиме `block` (нет процесса); ~1–2 МБ на недолго живущий bash в `notify`/таймере |
| Сервис + Telegram-бот (venv) | ~29 МБ | ~38–45 МБ |

## Запуск

Только сервис — ничего "запускать" вручную не нужно, `install.sh` сразу
ставит и включает systemd-юниты (`skipa-watchdog-sync-lists.timer` +
опционально `skipa-watchdog-notify.service`). Ручной прогон синхронизации:

```bash
sudo bash service/sync-lists.sh /opt/skipa_watchdog/service.conf
```

Сервис + бот:

```bash
python watchdog.py               # или: python watchdog.py /путь/к/config.yaml
```

При первом запуске сразу скачает базу IP и закэширует её в `data/ip_cache.json`,
дальше будет обновлять её раз в неделю (`sources.update_interval_days`).
Если `telegram.bot_token` заполнен — в этом же процессе поднимется и
Telegram-слой (`bot/telegram_layer.py`).

## Списки IP

Настройка называется по-разному в двух вариантах, но смысл один и тот же:
`ACTIVE_LIST` в `service.conf` (bash) или `sources.active_list` в
`config.yaml` (python) выбирает, что реально используется:

- **`list1`** — только основной список (CIDR-блоки из
  tread-lightly/CyberOK_Skipa_ips, `lists/skipa_cidr.txt`).
- **`list2`** — только дополнительный список (по умолчанию публичный gist).
  Формат смешанный и определяется автоматически построчно: CIDR
  (`1.2.3.0/24`), диапазон (`1.2.3.10-1.2.3.20`) или одиночный IP.
- **`merged`** (по умолчанию) — оба вместе, точные дубликаты убираются.

Переключить можно прямо из меню (`skipa-watchdog` → пункт 3 → 1) — правка
конфига руками не нужна.

## Команды в Telegram (если подключён)

- `/menu` — меню с инлайн-кнопками (статус, обновить базу, очередь, Docker/K8s, блокировки, помощь)
- `/status` — режим действия, активный список, сколько записей в базе, когда было
  последнее обновление, сколько IP заблокировано, сколько алертов в очереди на повтор
- `/update` — принудительно обновить базу IP прямо сейчас
- `/testalert [ip]` — прислать тестовое уведомление в нужном формате (по умолчанию
  на примере `203.0.113.42`), удобно для проверки форматирования
- `/pending` — сколько алертов сейчас в очереди на повтор из-за недоступности Telegram
- `/env` — обнаружены ли Docker/Kubernetes и стоит ли на их цепочках логирование/блокировка
- `/blocklist` — список заблокированных IP
- `/block <ip>` / `/unblock <ip>` — заблокировать/разблокировать IP вручную
- `/start` — краткая справка

Если в `config.yaml` задан `telegram.admin_ids`, команды будут работать только
для этих пользователей.

## Если Telegram недоступен

Даже без Telegram (или при временной недоступности связи) ничего не
теряется:

1. **Локальный лог всегда пишется**, в обоих вариантах установки. Каждое
   обнаружение попадает в `/var/log/skipa_watchdog/detections.log` (в bash-
   варианте — построчно из журнала ядра, в python-варианте — полный
   форматированный текст алерта) и `skipa-watchdog.log` (обычный
   процесс-лог).
2. **Очередь на повтор** (только python-вариант). Если Telegram настроен, но
   отправка не удалась (сеть легла, chat_id неверный и т.п.), сообщение
   складывается в очередь на диске и переотправляется каждые
   `alerting.retry_interval_seconds` (по умолчанию 5 минут), пока не уйдёт
   успешно.

## Важно про права доступа

Оба варианта обычно нужно запускать **от root** (или с capabilities
`CAP_NET_ADMIN`/`CAP_NET_RAW`), потому что управление `iptables`/`ipset`
(создание сетов, добавление/удаление правил и блокировок) требует
`CAP_NET_ADMIN`. В python-варианте чтение `/proc/net/tcp` (метод `poll`)
само по себе прав root не требует — только блокировка.

Все примеры systemd-юнитов в этом репозитории по умолчанию рассчитаны на
root.

## Docker и Kubernetes

Трафик, который идёт на порты, опубликованные через Docker (`docker run -p`
/ `ports:` в compose) или Kubernetes (`NodePort`/`LoadBalancer`), **не
проходит через обычный `INPUT`** — он маршрутизируется через собственные
цепочки iptables (`DOCKER-USER`, `KUBE-EXTERNAL-SERVICES`/`KUBE-NODEPORTS`).
Без дополнительной настройки такой трафик не логируется и не блокируется.

Пункт 5 меню `skipa-watchdog` (он же `sudo bash install.sh fw-rules`) решает
это автоматически — под капотом вызывает разный скрипт в зависимости от
установленного варианта:

- **Только сервис** — `service/setup-ipset-rules.sh`: для каждой найденной
  цепочки (`INPUT`, и если есть — `DOCKER-USER`, `KUBE-EXTERNAL-SERVICES`,
  `KUBE-NODEPORTS`) добавляет `-m set --match-set skipa-scanners/skipa-manual
  src` правила логирования и/или блокировки (в зависимости от `ACTION_MODE`).
- **Сервис + бот** — `install-firewall-rules.sh`: то же самое, но через
  динамическую цепочку `SKIPA-BLOCK`, в которую `watchdog.py` добавляет
  `-s <ip> -j DROP` при каждом обнаружении.

Оба скрипта идемпотентны — повторный запуск ничего не дублирует.

### Kubernetes и режим kube-proxy

Если `kube-proxy` работает в режиме **ipvs** (проверяется через
`ipvsadm -L -n`), цепочек `KUBE-*` в iptables нет вообще — в этом случае
оба скрипта выводят предупреждение и пропускают k8s-часть: логирование и
блокировка NodePort-трафика через этот механизм недоступны, остаётся
только защита хоста (`INPUT`).

### Автозапуск правил после перезагрузки

Правила iptables (и, в bash-варианте, содержимое ipset) не переживают
`reboot`, если не настроен `iptables-persistent`/`ipset persistent`. Чтобы
не терять их:

- **Только сервис** — `skipa-watchdog-sync-lists.timer` в любом случае
  перезаполняет `skipa-scanners` при каждом плановом запуске (по умолчанию
  раз в неделю), а `OnBootSec=10min` в самом таймере гарантирует прогон
  вскоре после каждой загрузки сервера. `iptables`-правила (переходы в
  `INPUT`/`DOCKER-USER`/`KUBE-*`) при этом не восстанавливаются
  автоматически — для этого настройте `iptables-persistent` (сохраняет
  правила) или добавьте `sudo bash install.sh fw-rules` в скрипт
  автозагрузки. Ручные блокировки (`skipa-manual`) при перезагрузке без
  `ipset persistent` теряются.
- **Сервис + бот** — `skipa-watchdog-fw-rules.service` (systemd-юнит)
  применяет правила после старта Docker/kubelet при каждой загрузке
  (нужно включить: `sudo systemctl enable skipa-watchdog-fw-rules`), а сам
  список заблокированных IP `watchdog.py` дублирует в `data/blocked_ips.json`
  и накатывает обратно на iptables при каждом своём старте.

## Расширенный мониторинг через nftables/iptables (надёжнее, ловит одиночные SYN)

Актуально только для варианта **сервис + бот** (bash-вариант и так матчит
каждый пакет через ipset на уровне ядра — см. раздел "Как это работает"
выше, дополнительно настраивать нечего).

`monitoring.method` в `config.yaml` может быть:

- **`poll`** — периодический опрос активных TCP-соединений напрямую из
  `/proc/net/tcp`/`/proc/net/tcp6` (без сторонних библиотек). Не требует
  прав root для самого мониторинга (но они всё равно нужны для блокировки).
  Может пропустить очень короткое соединение между двумя опросами.
- **`kernel_log`** — читает строки `CONN: ...`, которые сам сервер пишет в
  журнал ядра благодаря правилу `LOG`, поставленному
  `install-firewall-rules.sh`. Видит вообще каждый SYN-пакет, даже если
  соединение сразу же оборвалось.
- **`both`** (по умолчанию) — оба метода одновременно (дедупликация по
  `alert_cooldown_minutes` убирает повторные срабатывания на один и тот же
  IP). Безопасно как значение по умолчанию, потому что `install.sh`
  **всегда** ставит нужное `LOG`-правило при первой установке.

## Запуск как systemd-сервис

Обычно делает `install.sh` сам (пункт установки/обновления). Вручную —
только сервис:

```bash
sudo cp service/skipa-watchdog-sync-lists.service /etc/systemd/system/
sudo cp service/skipa-watchdog-sync-lists.timer /etc/systemd/system/
sudo cp service/skipa-watchdog-notify.service /etc/systemd/system/   # если нужен detections.log
sudo systemctl daemon-reload
sudo systemctl enable --now skipa-watchdog-sync-lists.timer
sudo systemctl enable --now skipa-watchdog-notify   # опционально
```

Вручную — сервис + бот:

```bash
sudo cp skipa-watchdog.service /etc/systemd/system/
sudo nano /etc/systemd/system/skipa-watchdog.service   # поправить путь ExecStart
sudo systemctl daemon-reload
sudo systemctl enable --now skipa-watchdog
sudo journalctl -u skipa-watchdog -f

# + автоприменение правил iptables после каждой перезагрузки
sudo cp skipa-watchdog-fw-rules.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now skipa-watchdog-fw-rules
```

## FAQ

**Чем принципиально отличаются два варианта установки, а не просто "с ботом/без бота"?**
Это две независимые реализации одной и той же защиты. "Только сервис" не
просто "бот без Telegram-части" — там в принципе нет Python, нет `venv`, нет
кэша базы в виде python-объектов: вся логика на bash, а обнаружение и
блокировка целиком делегированы ядру через `ipset`/`iptables`. Это сделано
специально, чтобы сервер, которому не нужен Telegram, не получал вместе с
защитой лишний интерпретатор и его зависимости.

**Почему в "только сервис" два ipset (skipa-scanners и skipa-manual), а не один?**
`skipa-scanners` целиком пересобирается при каждом обновлении списка
(`ipset swap`) — если ручные блокировки хранить в нём же, они бы стирались
при каждом таком обновлении. `skipa-manual` — отдельный набор, который
трогает только администратор (пункт меню 6 / `blockctl.sh`), поэтому
переживает любое количество автообновлений базового списка.

**Нужны ли для Docker/Kubernetes какие-то особые пакеты?**
Нет. Работа идёт только через `iptables`/`ipset` (в bash-варианте) или
`iptables` (в python-варианте) — оба обычно уже стоят вместе с Docker как
его зависимости. Отдельный демон nftables не используется и не нужен.
Единственное, что важно соблюсти — **порядок запуска**: правила в
`DOCKER-USER`/`KUBE-*` можно ставить только после того, как Docker/kubelet
создали эти цепочки, поэтому systemd-юнит явно объявляет
`After=docker.service` (и `After=kubelet.service`, если он есть).

**Нужен ли root?**
Обычно да, см. раздел "Важно про права доступа" выше.

**Что если на сервере нет systemd?**
`install.sh` рассчитан на systemd (все юниты — `.service`/`.timer`). Без
systemd можно запускать скрипты вручную по cron: `service/sync-lists.sh` по
расписанию и `service/setup-ipset-rules.sh` один раз при старте сети (после
Docker, если он есть).

**Я случайно заблокировал свой же IP (или легитимного клиента) — что делать?**
`skipa-watchdog` → пункт 6 "Заблокированные IP" → разблокировать. В
bash-варианте это снимет блокировку, только если IP был добавлен вручную
(`skipa-manual`) — если он пришёл из автообновляемого базового списка,
добавьте его в `IGNORE_IPS` в `service.conf`, чтобы исключить насовсем. В
варианте с ботом — `/unblock <ip>` в Telegram или та же команда меню.

**Список сканеров может по ошибке зацепить что-то легитимное?**
Теоретически да, как и с любым готовым чёрным списком — списки собираются
сторонними исследователями (CyberOK/tread-lightly, автор gist-а). Если
уверены, что конкретный IP не должен блокироваться, добавьте его в
`IGNORE_IPS` (bash) / `monitoring.ignore_ips` (python) — он никогда не
будет считаться сканом, даже если попадёт в список.

**Можно логировать, но не блокировать (например, чтобы сначала понаблюдать)?**
Да, режим действия `notify` (пункт меню 3 → 2 → "Только уведомлять") в
обоих вариантах установки.

**Что будет, если Telegram временно недоступен?**
Ничего не теряется — сообщение уходит в очередь на диске и переотправляется
каждые `alerting.retry_interval_seconds` (по умолчанию 5 минут), плюс
локальный лог (`detections.log`) пишется в любом случае, независимо от
Telegram.

**Как посмотреть, что вообще происходит, без Telegram?**
`skipa-watchdog` → пункт 1 "Проверка работоспособности" (сводка) или пункт 8
"Просмотр логов" (`journalctl`, `detections.log`, `skipa-watchdog.log`).

**Как обновить базу IP прямо сейчас, не дожидаясь недели?**
`skipa-watchdog` → пункт 7, либо `/update` в Telegram, либо
`sudo bash install.sh check-lists` (только проверить, вышло ли что-то новое,
без скачивания полной базы).

```
skipa_watchdog/
├── install.sh                       # установщик/менеджер: первый запуск = выбор варианта, дальше - меню
├── VERSION                          # версия проекта (читается меню install.sh)
│
├── service/                         # "только сервис" - чистый bash, без Python
│   ├── service.conf.example           # шаблон конфига (обычный bash KEY="value", не YAML)
│   ├── sync-lists.sh                  # скачивает/объединяет списки, атомарно грузит в ipset skipa-scanners
│   ├── setup-ipset-rules.sh           # ставит iptables-правила (INPUT/DOCKER-USER/KUBE-*) под оба ipset
│   ├── notify-tail.sh                 # (опц.) хвостует journalctl -k, пишет detections.log
│   ├── blockctl.sh                    # ручные блокировки (ipset skipa-manual): block/unblock/list
│   ├── skipa-watchdog-sync-lists.service/.timer  # systemd: периодическое обновление списка
│   └── skipa-watchdog-notify.service   # systemd: демон detections.log (если ACTION_MODE включает notify)
│
├── watchdog.py                      # "сервис + бот" - единая точка входа: мониторинг + блокировка + Telegram
├── config.example.yaml              # шаблон конфига python-варианта
├── requirements.txt                 # базовые зависимости python-варианта (только PyYAML)
├── requirements-telegram.txt        # доп. пакет python-telegram-bot - только если нужен Telegram
├── install-firewall-rules.sh        # ставит SKIPA-BLOCK + переходы + CONN-логирование (INPUT/DOCKER-USER/KUBE-*)
├── skipa-watchdog-fw-rules.service  # systemd-юнит: применяет правила после старта Docker/kubelet
├── skipa-watchdog.service           # systemd-юнит: сам watchdog.py
├── bot/
│   ├── config.py             # загрузка config.yaml
│   ├── ip_lists.py           # скачивание/кэш/обновление базы IP (list1/list2/merged), проверка новых версий
│   ├── blocker.py            # блокировка через iptables (цепочка SKIPA-BLOCK), персистентность блокировок
│   ├── env_detect.py         # определение Docker/Kubernetes, статус правил логирования/блокировки
│   ├── telegram_layer.py     # необязательный слой Telegram: команды, инлайн-меню, отправка уведомлений
│   ├── http_client.py        # минимальный HTTP-клиент на urllib (без aiohttp)
│   ├── enrich.py              # ipinfo.io + RIPEstat + ipregistry.co
│   ├── formatter.py          # сборка текста алерта в нужном стиле
│   ├── monitor.py            # мониторинг: /proc/net/tcp и/или чтение kernel-лога
│   └── fallback.py           # audit-лог + очередь на повтор при недоступности Telegram
│
├── data/                              # (режим bot) создаётся автоматически
│   ├── ip_cache.json               # локальный кэш базы IP
│   ├── list_versions.json           # хэши листов для проверки новых версий
│   ├── blocked_ips.json             # список заблокированных IP (для восстановления после reboot)

    ├── skipa-watchdog.log              # общий процесс-лог
    └── detections.log                   # audit-журнал всех обнаружений
```
