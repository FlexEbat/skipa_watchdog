[![XERJ Corpus Hub contributor](https://hub.xerj.org/contributors/FlexEbat/badge.svg)](https://hub.xerj.org/contributors/FlexEbat)

Skipa Watchdog блокирует на вашем сервере подключения от известных сканеров (CyberOK/Skipa, ГРЧЦ,
НКЦКИ и дополнительные списки) и по желанию присылает уведомление в Telegram или Matrix. Защита
работает на хосте и для сервисов, опубликованных через Docker и Kubernetes.

- **Блокировка в ядре.** Списки загружаются в `ipset`, сканер отсекается на первом пакете. Постоянного
  процесса для блокировки нет.
- **Только bash.** `iptables`, `ipset`, `curl`, `systemd`. Python не нужен ни для установки, ни для работы.
- **Всё автоматически.** Список обновляется по таймеру, блокировка ставится сама, ручной блокировки и
  разблокировки нет. Единственный ручной рычаг: белый список.
- **Уведомления по желанию.** Telegram и/или Matrix, одним сообщением на волну сканов. Без них работают
  локальные логи.
- **Самовосстановление.** После перезагрузки ipset-наборы и правила возвращаются сами.
- **Защита от самоблокировки.** Служебные сети и ваши SSH-сессии заблокировать нельзя.

## Быстрый старт

Нужен root и `git` (если его нет, `install.sh` доустановит сам; `iptables`, `ipset` и `curl` тоже).

```bash
curl -fsSL https://raw.githubusercontent.com/FlexEbat/skipa_watchdog/main/install.sh -o install.sh
sudo bash install.sh
```

Установщик покажет описание, скачает списки, соберёт `ipset` и применит правила `iptables`. Код
ставится в `/opt/skipa_watchdog`, логи пишутся в `/var/log/skipa_watchdog`. Дальше управляйте командой:

```bash
sudo skipa-watchdog
```

Пункты меню: 1 проверка работоспособности, 2 управление сервисом, 3 настройки обнаружения, 4 уведомления,
5 Docker/Kubernetes, 6 заблокированные IP (просмотр), 7 белый список, 8 статистика, 9 обновить базу,
10 логи, 11 редактировать конфиг, 12 обновить проект, 13 удалить. При каждом запуске меню проверяет, не
вышла ли новая версия проекта, и предлагает установить её.

Без меню:

```bash
sudo bash install.sh install       # установить или обновить
sudo bash install.sh status        # краткий статус
sudo bash install.sh fw-rules      # применить правила Docker/Kubernetes
sudo bash install.sh check-lists   # проверить новые версии списков
sudo bash install.sh test-notify   # отправить тестовое сообщение в Telegram/Matrix
sudo bash install.sh stats [дней]  # статистика детектов
sudo bash install.sh uninstall     # удалить (с предложением убрать правила и ipset)
```

**Сразу после установки впишите свой SSH-IP** в белый список (пункт 7 меню), если он статический.

## Как это работает

```
списки IP ──► sync-lists.sh (по таймеру) ──► ipset skipa-scanners ──► DROP в ядре (INPUT, DOCKER-USER, KUBE-*)
                                                      │
                                    LOG-правило ──► журнал ядра ──► notify-tail.sh ──► detections.log
                                                                                  └──► Telegram / Matrix
```

**Блокировка.** В `iptables` стоят правила, которые сверяют адрес отправителя с наборами `ipset`:
`skipa-scanners` (списки), `skipa-manual` (бессрочные блокировки, перенесённые со старой версии) и
`skipa-allow` (белый список). Всё решает ядро, процессов пользовательского пространства для блокировки нет.

**Обнаружение и уведомления.** LOG-правило пишет первый пакет сканера в журнал ядра, а
`skipa-watchdog-notify.service` читает его (`journalctl -k`), пишет `detections.log` и отправляет
уведомление. Одно и то же IP не пишется и не отправляется чаще, чем раз в `alert_cooldown_minutes`.

**Режимы действия** (`action.mode`, пункт 3 меню):

| режим | блокировка | запись в журнал и уведомления |
| --- | --- | --- |
| `block_notify` (по умолчанию) | да | да |
| `block` | да | нет (демон `notify` не запускается) |
| `notify` | нет | да |

## Конфигурация

Единый файл `config.yaml` (шаблон: [`config.example.yaml`](config.example.yaml), все параметры описаны
комментариями). Проще всего менять его через меню; после правки вручную примените изменения (пункт 11
предложит это сам).

| ключ | по умолчанию | назначение |
| --- | --- | --- |
| `action.mode` | `block_notify` | режим действия |
| `sources.active_list` | `merged` | какие списки использовать: `list1`, `list2`, `merged` |
| `sources.primary_list_url`, `blacklist_url` | см. шаблон | адреса списков |
| `sources.update_interval_days` | `7` | как часто обновлять базу |
| `sources.min_prefix` | `20` | самая широкая сеть из списков (длина префикса); для Spamhaus DROP поставьте `16` |
| `sources.allow_insecure_http` | `false` | разрешить скачивание списков по обычному http (по умолчанию только https) |
| `sources.min_entries` | `10` | минимум записей в источнике при ПЕРВОЙ загрузке (защита от списка-«мусора» из трёх строк) |
| `sources.extra` | пусто | дополнительные источники |
| `firewall.keep_established_tcp` | `false` | не рвать установленные TCP-сессии: блокировать только новые TCP-соединения (SYN) и весь не-TCP трафик. Осторожно: сканер, успевший открыть сессию, продолжит работать в её рамках. После смены примените правила заново (пункт 5) |
| `firewall.log_limit`, `log_burst` | `30/second`, `40` | лимит LOG-правила |
| `monitoring.ignore_ips` | пусто | адреса, которые не блокируются |
| `monitoring.auto_allowlist`, `ssh_ports` | `true`, `[22]` | не блокировать IP текущих SSH-сессий |
| `monitoring.alert_cooldown_minutes` | `60` | не повторять запись по одному IP чаще |
| `monitoring.kernel_log_prefix` | `CONN: ` | префикс LOG-правила в журнале ядра |
| `telegram.*`, `matrix.*` | пусто | каналы уведомлений |
| `notifications.batch_seconds`, `batch_max` | `30`, `20` | сколько секунд копить сообщения и сколько адресов перечислять |
| `notifications.language` | `ru` | язык текста сообщений: `ru` или `en` |
| `environment.docker_scan`, `k8s_scan` | `true` | подключать ли правила к `DOCKER-USER` и `KUBE-*` |
| `logging.log_dir` | `/var/log/skipa_watchdog` | каталог логов |

Источники по умолчанию:

- **Список 1** — [tread-lightly/CyberOK_Skipa_ips](https://github.com/tread-lightly/CyberOK_Skipa_ips)
  (CyberOK/Skipa, ГРЧЦ, НКЦКИ).
- **Список 2** — blacklist от [sngvy](https://gist.github.com/sngvy/07cee7ac810c9d222fbebddff8c1d1b8)
  (CIDR, диапазоны и одиночные IP; включает сети сканеров вроде Censys).

Оба скачиваются всегда, `active_list` выбирает, какие записи попадут в набор. Если источник недоступен или
вернул вдвое меньше записей, чем раньше, используется его прошлая версия. Сети шире `sources.min_prefix`
отбрасываются, а источник, который целиком покрывает больше ~4 млн адресов, не принимается: так «раздутый»
чужой список не заблокирует пол-интернета. Списки скачиваются только по https, редирект на http отклоняется.
Записи вида `1.2.3.0/24/мусор` отбрасываются целиком.

## Защита от самоблокировки

Списки внешние, а блокировка автоматическая, поэтому заблокировать нельзя:

- loopback, частные сети (`10/8`, `172.16/12`, `192.168/16`) и link-local;
- адреса из `monitoring.ignore_ips`;
- IP с открытыми SSH-сессиями на `monitoring.ssh_ports` (`monitoring.auto_allowlist`): их раз в минуту
  добавляет `skipa-watchdog-allow-ssh.timer`;
- сети короче `/16` (в том числе `0.0.0.0/0`), IPv6 и всё, что пересекается с белым списком.

## Docker и Kubernetes

Трафик на опубликованные порты контейнеров идёт через цепочку `FORWARD`, а не `INPUT`. Поэтому правила
ставятся и в `DOCKER-USER`, и (если есть) в `KUBE-EXTERNAL-SERVICES`, `KUBE-NODEPORTS`. Установщик находит
их сам; повторно применить правила можно из меню (пункт 5) или `sudo bash install.sh fw-rules`. Отключить
цепочки: `environment.docker_scan: false`, `environment.k8s_scan: false`.

## Уведомления: Telegram и Matrix

Это только отправка сообщений: команд в чате нет, ботом не нужно управлять, а Python не нужен. Всё делает
`curl` из bash. Настройка: пункт 4 меню (токены вводятся без показа на экране и проверяются по формату до
записи в `config.yaml`), проверка: `sudo bash install.sh test-notify`.

**Telegram.** Создайте бота у [@BotFather](https://t.me/BotFather), добавьте его в чат или канал и укажите
токен и `chat_id` (у групп он отрицательный). Если Telegram недоступен напрямую, задайте `telegram.proxy`
(`http://`, `https://`, `socks5://`, `socks5h://`).

**Matrix.** Нужны адрес homeserver (`https://matrix.example.org`; `http` допускается только для
localhost), `access_token` пользователя или бота и `room_id` вида `!abc:example.org` (не алиас
`#комната`). Пользователь должен уже состоять в комнате.

Можно включить оба канала сразу. Что гарантируется:

- **Одно сообщение на волну.** Обнаружения копятся `notifications.batch_seconds` секунд (по умолчанию
  30) и уходят списком до `batch_max` адресов; остальное - строкой «и ещё N».
- **Очередь с повторами.** Сообщение сначала кладётся в очередь (`/var/lib/skipa_watchdog/notify-spool`),
  по файлу на канал. При сетевой ошибке и ответах 5xx отправка повторяется, порядок сохраняется; при 429
  выдерживается пауза из `retry_after` (не дольше 60 с). Если сервер отвечает 400/401/403/404 (неверный
  токен, чат или комната), сообщение выбрасывается с записью в `skipa-watchdog.log`, а не копится вечно.
  Сообщения старше суток и всё, что сверх 200 файлов, выбрасываются. Matrix получает один и тот же
  `txnId` при повторе, поэтому дублей не будет.
- **Секреты не попадают в `ps`.** Адрес с токеном и заголовок `Authorization` передаются в `curl` через
  stdin (`-K -`), а не аргументами.
- **Простой текст.** Без HTML и Markdown, поэтому экранировать нечего.

Пример сообщения:

```
Skipa Watchdog @ my-server
Обнаружено сканеров: 3 (заблокирован ядром)
• 203.0.113.42  TCP/22
• 203.0.113.43  TCP/443
• 198.51.100.7  UDP/3478
```

Уведомления отправляет демон `skipa-watchdog-notify`, а он запускается только при `action.mode` с
уведомлением (`notify`, `block_notify`). Если включить канал при режиме `block`, меню предложит
переключить режим на `block_notify`.

## Дополнительные источники

`sources.extra` в `config.yaml`: Spamhaus DROP, FireHOL, AbuseIPDB или свой список. Типы `cidr_list`
(простой текстовый список, комментарии `#` и `;`) и `abuseipdb` (нужен свой `api_key`, поле
`min_confidence`), у каждого можно задать `min_entries`. Участвуют независимо от `active_list`, пока
`enabled: true`. Только IPv4: записи IPv6 пропускаются с записью в журнал.

Fail2ban можно использовать как альтернативу блокировке в ядре: фильтр и jail из [`fail2ban/`](fail2ban)
банят по `detections.log`.

## Эксплуатация

**Логи.**

| что | где |
| --- | --- |
| обнаружения | `/var/log/skipa_watchdog/detections.log` |
| процесс, ошибки уведомлений | `/var/log/skipa_watchdog/skipa-watchdog.log` |
| список и демон | `journalctl -u skipa-watchdog-sync-lists -u skipa-watchdog-notify` |

Ротацию логов (`/etc/logrotate.d/skipa-watchdog`) ставит установщик.

**Перезагрузка и правила.** Ipset-наборы и правила живут только в памяти ядра, поэтому они сохраняются и
возвращаются при загрузке (`/var/lib/skipa_watchdog/ipsets.save`, обновляется после каждой синхронизации и
каждого изменения белого списка):

- `skipa-watchdog-ipset.service` — рано, до `netfilter-persistent`: восстанавливает наборы (а если файла
  нет — создаёт пустые). Это важно: если на сервере сохранены правила со ссылками на `skipa-*`, а наборов
  ещё нет, `iptables-restore` отвергает весь файл правил целиком, и сервер остаётся без фаервола вообще;
- `skipa-watchdog-rules.service` — позже, после Docker и kubelet (им нужны цепочки `DOCKER-USER` и
  `KUBE-*`): ставит правила и проверяет результат;
- `skipa-watchdog-sync-lists.timer` обновляет списки через 10 минут после загрузки и затем по расписанию.

Юнит один нельзя: `After=docker.service` вместе с `Before=netfilter-persistent.service` образует цикл
упорядочивания, и systemd разорвал бы его, удалив случайное задание.

Все операции с наборами (таймер, пункт 9 меню, `blockctl.sh`, применение правил, загрузка) идут под одним
`flock` (`/var/lib/skipa_watchdog/ipset.lock`), поэтому не пересекаются. После применения правил скрипт
проверяет, что наборы существуют, а в `INPUT`, `DOCKER-USER` и `KUBE-*` стоят правила, и сообщает итог
(`✓`/`✗`); то же показывает пункт 1 меню.

**Белый список.** Пункт 7 меню или `sudo bash service/blockctl.sh allow|unallow|allowlist [ip]`: запись в
`config.yaml` и в `ipset` сразу. Ручной блокировки и разблокировки нет: всё работает автоматически.

**Юниты.** Работают от root (нужны `iptables`, `ipset`, журнал ядра). Включены ограничения systemd, не
мешающие работе: `NoNewPrivileges`, `PrivateTmp`, `PrivateDevices`, `ProtectSystem=full`,
`RestrictNamespaces`, `RestrictAddressFamilies` и т. п.; у демона уведомлений дополнительно
`ProtectKernelModules`/`ProtectKernelTunables`. Строгая песочница для юнитов с `iptables` не используется:
`iptables` подгружает модули ядра, и она ломала запуск на части систем.

**Обновление.** При каждом запуске панели (`sudo skipa-watchdog`) проверяется, не вышла ли новая версия, и
предлагается установить её; отказ не навсегда: напоминание остаётся в шапке меню. `SKIPA_NO_UPDATE_CHECK=1`
отключает проверку разово, `sudo bash install.sh check-update` проверяет без вопросов (код 10 — есть
обновление). Вручную: пункт 12 меню или `sudo bash install.sh install`. Если `git pull` не проходит (история
в репозитории изменилась), установщик предложит перейти на актуальную версию: `config.yaml` и `data/` не
затрагиваются.

**Удаление.** Пункт 13 меню. Установщик отдельно спросит, убрать ли правила `iptables` и наборы `ipset`.

## Переход с версий с Python-ботом

Начиная с 4.0 Python из проекта убран. Если у вас стоял вариант «сервис + Telegram-бот», обновление
(`sudo skipa-watchdog` → пункт 12, или `sudo bash install.sh install`) переведёт его на bash само, без
перерыва в защите: сначала поднимаются bash-юниты и правила `ipset`, и только потом убираются юнит бота,
цепочка `SKIPA-BLOCK` и наборы `skipa-dyn`/`skipa-db`, а venv удаляется.

- **Сохраняется:** `config.yaml` (токен и `chat_id` Telegram продолжают работать как уведомления),
  `data/`, белый список и бессрочные ручные блокировки (они переносятся в `skipa-manual`).
- **Пропадает:** блокировки на срок (в том числе автоблокировки; они истекли бы сами), команды в чате
  (`/block`, `/allow`, `/stats` и другие), кнопка «Забанить», дашборд, обогащение алертов (страна, ASN),
  недельный дайджест и health-check бота. Блокировку заменяет белый список, остальное уже не нужно.

## Безопасность

- `config.yaml` содержит токены: установщик выставляет права `600`, а при любых секретах в конфиге и
  других правах предупреждает.
- Токены передаются в `curl` через stdin, а не аргументами, и не видны в `ps`.
- Значения из меню проверяются по формату до записи (токен Telegram, `chat_id`, `homeserver`, `room_id`), а
  запись в `config.yaml` не раскрывает `\n` и отвергает кавычки, обратный слэш и переводы строк, которыми
  можно было бы подсунуть чужие ключи.
- Журнал ядра очищается от управляющих символов перед записью в `detections.log` (иначе можно подделать
  соседние записи для fail2ban).
- Защита от самоблокировки описана выше. Если вас всё же отрезало, зайдите через консоль хоста и выполните
  `sudo skipa-watchdog`: внесите свой IP в белый список (пункт 7); пункт 13 удаляет проект вместе с правилами.
- Обновление проекта — это `git pull` из репозитория с правами root: тот, кто управляет репозиторием,
  управляет и вашими серверами. Включите 2FA на аккаунте GitHub, закрепите `SKIPA_REPO_URL` на свой форк,
  если хотите читать изменения перед обновлением.
- Об уязвимостях сообщайте владельцу репозитория лично, не в публичных issue.

## Вопросы и проблемы

**Пришло уведомление на IP, которого «нет в правилах».** Проверьте, входит ли адрес в какой-то из списков,
включая диапазоны во втором списке:

```bash
sudo ipset test skipa-scanners 66.132.186.215
```

Сети сканеров в списках шире одного адреса: например, `66.132.186.215` входит в `66.132.186.0/24` из
второго списка. Запись создаёт любой пакет от сканера: LOG-правило срабатывает на все протоколы (в
`detections.log` видно `proto=UDP port=3478`), а пакет после записи отбрасывается.

**Уведомления не приходят.** Пункт 4 → «Отправить тестовое сообщение» покажет итог по каждому каналу:
«доставлено», «сервер отклонил запрос» (неверный токен, `chat_id` или комната) или «нет связи». Проверьте
также, что `action.mode` не `block` и что демон жив: `systemctl status skipa-watchdog-notify`. Ошибки отправки
пишутся в `skipa-watchdog.log`. Пункт 1 меню показывает размер очереди неотправленных сообщений.

**Ложное срабатывание на легитимный сканер** (например, ваш мониторинг безопасности): добавьте его IP в
белый список (пункт 7).

**Блокировка не работает для контейнеров.** Откройте пункт 5 меню → «Показать текущие правила»: правила
должны быть и в `DOCKER-USER`. Если Docker запустился позже, примените правила заново (пункт 5; при загрузке
это делает `skipa-watchdog-rules.service`).

## Разработка

```bash
python3 -m unittest discover -s tests -t .     # 100+ тестов, root не нужен
shellcheck -S warning install.sh service/*.sh
```

Сам проект — чистый bash; Python нужен только тестам (они запускают bash-скрипты) и PyYAML для проверки
`config.yaml`. Тесты подменяют `iptables`, `ipset`, `curl` и `journalctl` имитацией
([`tests/netfake.py`](tests/netfake.py) и поддельные скрипты в самих тестах) и не трогают настоящий
фаервол и сеть. Сквозной сценарий на настоящих `ipset`/`iptables` (перезагрузка, `iptables-restore`, flock)
включается явно, потому что меняет наборы и правила хоста:
`SKIPA_REAL_NETFILTER_TESTS=1 python3 -m unittest tests.test_real_netfilter` от root в одноразовой среде.

Структура:

```
install.sh             установщик и меню
service/               скрипты: списки, правила, уведомления, чтение config.yaml, белый список
fail2ban/              фильтр и jail (альтернативный способ бана)
tests/                 тесты
config.example.yaml    шаблон конфига
```
